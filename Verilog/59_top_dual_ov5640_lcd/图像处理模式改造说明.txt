系统性修复（2026-10-03 第二轮）
--------------------------------
【重要】这一轮一次改了四项并直接烧录，结果板子全黑，随后又出现识别框抖动。
两项已回退，两项保留。教训记在这里：一次只上一项、上板前先用仿真验证。

  回退【1】pin.xdc 两台摄像头时钟改名  -> 造成全黑
  回退【2】bin_morph_3x3 的 1 像素斜切修复 -> 造成识别框抖动
  保留【3】摄像头帧率计
  保留【4】死代码清理

【1】pin.xdc 时钟改名 —— 已回退，原因：全黑
  当时把两条同名的 create_clock 改成 cmos_pclk_1 / cmos_pclk_2。
  改之前 cam_pclk_1 实际是【未约束】的（第二条覆盖第一条），Vivado 把它
  当普通网络走线；改之后它变成正式时钟、必须占用时钟缓冲与专用时钟网络。
  这个改动让整块板子显示全黑，回退后立刻恢复。
  观察：被分析的时序端点从 26686 涨到 28723（+2037），说明改后确实多约束了
  cam_pclk_1 那一整个时钟域。也就是说那个域从来没被时序分析过 —— 这是个
  真实的隐患，但不能靠直接改时钟名来解决，需要单独评估（可能要改用
  set_clock_groups 或先确认 cam_pclk_1 所在引脚是否时钟专用引脚）。

【2】bin_morph_3x3 斜切修复 —— 已回退，原因：识别框抖动
  原写法：
      r1 <= line1[x];  r2 <= line2[x];  ...  q0 <= r1;  s0 <= r2;
  我改成直接读 line1[x] / line2[x]。
  分析：行缓存被推断成 BRAM（DRC 告警里明确写着 RAMB18），BRAM 输出本身
  就是同步/带输出寄存器的。抽掉 r1/r2 等于抽掉一级流水，q/s 两行相对 p 行
  的时序关系随之改变 —— 表现就是识别框变抖。
  回退后在代码里留了详细注释，说明这个斜切是"已知且有意保留"的，
  任何未来的修复必须先在 xsim 里对这个模块单独仿真验证过才能上板。
  bin_morph_3x3 是自包含模块，仿真成本很低，当时跳过了这一步是流程错误。

【3】摄像头帧率计 —— 保留
  延迟账本里唯一没定的数就是摄像头帧率。加了两根自校准条：
     青色条 = 每个摄像头帧走 4 像素
     品红条 = 每个 LCD 帧走 4 像素
  两者都在屏幕底部同一行、同一拍摄条件下，所以手机录像的缩放自动抵消：
     fps_cam = fps_lcd × (青条速度 / 品红条速度)
  而 fps_lcd 从屏幕时序精确已知 = 480x272, pclk 12.5MHz, 525x286 总计 = 83.2 Hz。
  KEY3 打开诊断时才显示（follow_enable 上电默认为 0，所以平时看不见）。

【4】死代码清理 —— 保留
  video_alg_top.v  删除 target_rg_diff / target_rb_diff（旧色彩模板检测器残留）
  top_dual_ov5640_lcd.v  删除 key0_press（KEY0 改释放沿判定后不再使用）
  注：cmos_frame_href_1/2 一开始看着像死信号，实际接到了写入侧跟踪器的 .href
      输入（top L403/L419），是活的，保留。

下面是这一轮各项的原始分析，留档。
--------------------------------
一次性处理了排查出来的几个结构性问题。

【1】修 pin.xdc：两台摄像头的像素时钟同名覆盖
  旧:
    create_clock -period 40.000 -name cmos_pclk [get_ports cam_pclk_1]
    create_clock -period 40.000 -name cmos_pclk [get_ports cam_pclk_2]
  两条 create_clock 用了同一个名字，第二条把第一条覆盖掉（综合告警
  Constraints 18-619 × 2）。后果比想象严重：被分析的时序端点从 26630
  涨到 28723（+2093），说明以前 cam_pclk_1 那一整个时钟域**根本没进时序分析**。
  新:
    create_clock -period 40.000 -name cmos_pclk_1 [get_ports cam_pclk_1]
    create_clock -period 40.000 -name cmos_pclk_2 [get_ports cam_pclk_2]
  修完告警归零，且时序仍然全部满足。

【2】修 bin_morph_3x3 的 1 像素斜切（rtl/red_ycbcr_morph.v）
  旧写法的行缓存多打了一拍：
      r1 <= line1[x];  ...  q0 <= r1;      // q 行比 p 行晚一个像素
  导致 p 行取 X-2..X 列、q/s 行取 X-3..X-1 列，3x3 结构元实际是平行四边形，
  形态学结果有约 1 像素的方向性偏差。
  新写法直接读缓存（非阻塞赋值天然取到写入前的值 = 第 Y-1 / Y-2 行第 X 列）：
      q0 <= line1[x];  s0 <= line2[x];
  现在三行严格对齐，是真正的正方形结构元。
  注意：这会让红色 mask 整体有约 1 像素位移，跟框位置可能有零点几像素变化。

【3】摄像头帧率计（自校准）
  延迟账本里唯一没定的数就是摄像头帧率。加了两根自校准条：
     青色条 = 每个摄像头帧走 4 像素
     品红条 = 每个 LCD 帧走 4 像素

  KEY3 打开诊断时才显示。

【4】死代码清理

红色判据修正（重要，2026-10-03）
--------------------------------
症状：绿框偶尔识别不上；识别上以后红绿框乱闪；距离在 171 / 155 / 68 / ---- 之间乱跳。

定位过程：
  用延迟探头看现场，发现红框明显偏离红目标。把录像里 LCD 的画面按 FPGA 的
  YCrCb 公式重算了一遍掩码，得到左半屏的掩码分布：

    簇  x 范围    像素  Cr   Cb   Cr-Cb   是什么
    B   104~137  1062  182   96     86    红目标本体
    C   143~149    42  153  104     49    橙色杂物边缘
    D   170~173    30  154  106     49    橙色杂物

  红物体本体 Cr-Cb 中位数 = 78，而杂物只有 22 和 -10，分得很开。
  但旧判据的 cr > cb + 40 把杂物放进来了 9~11%，这就足以把外接矩形中心
  从 120 拽到 138（偏 18 像素）。跟踪器靠 ±50 搜索窗勉强锁住目标，所以
  平时看着还行；一旦丢锁窗口张开（A 改动把它一下子开到 120），杂物立刻
  进入统计范围，框就跳走了 —— 这就是"乱闪"。同时双目测距的 ROI 也把杂物
  算了进去，左右视差算错，距离就乱跳。

  为什么"识别不上"：判据太松时红像素质心被杂物拉偏，目标快速移动时
  更容易掉出搜索窗。

修复：rtl/red_ycbcr_morph.v 的红色判据
    旧: (cr>=150) && (cb<=120) && (cr > cb+40)
    新: (cr>=155) && (cb<=118) && (cr > cb+55)

  实测效果（同一帧）：
    旧判据: 红物体保留 62.1%，杂物C 9.2%，杂物D 11.5%，bbox 中心 138（偏）
    新判据: 红物体保留 57.6%，杂物C 0%，  杂物D 0%，  bbox 中心 120（正中）

  主要收紧的是差值项 cr-cb，它对摄像头/显示屏的色彩标定误差不敏感，
  比单纯抬高 Cr 门限更稳。

  这个模块是三处共用的（写入侧两台摄像头各一个 u_morph，读侧一个
  u_red_ycbcr_morph），所以改一处，跟踪、测距、二值化显示全都跟着收紧。

如果换了目标物体或光照后发现判据过严（红物体保留太少、框断续），
把 cr8 > (cb8 + 9'd55) 里的 55 往下调到 48 左右即可。

改了什么
--------
对照视频《2025年FPGA创新设计赛道 安路二 双目视觉处理系统》的
「基础要求二：视频图像实时处理算法」，补齐了它那 8 个算法页面里我们缺的部分。

模式表（KEY0 短按循环，LED[2:0] 显示模式号）
  0  原始图像        RAW
  1  二值化          BINARY     灰度双阈值，低/高阈值可调
  2  腐蚀            ERODE      3x3，作用在二值图上
  3  开运算          OPEN       先腐蚀后膨胀
  4  浮雕效果        EMBOSS
  5  拉普拉斯锐化    LAPLACIAN
  6  Sobel 边缘      SOBEL
  7  跟随测距        DEPTH      绿框跟随红目标 + 距离数值

模式 7「跟随测距」
------------------
这个是本次重点做的功能。它的三个东西是同一套：
  屏幕上的绿框  =  红像素统计的窗口  =  算距离用的视差来源
所以框跑到哪，测的就是哪，数值和框永远对得上。

  每半屏一个框，左框跟左目红目标、右框跟右目红目标，互相独立。
  框大小固定 50x50（half = 25），以目标框中心为中心，自动夹在画面内。
  还没锁到目标时，框退回到该半屏的中心位置。

  框大小怎么调：rtl/stereo_red_ruler.v 里改 DYN_HALF_W / DYN_HALF_H 这两个
  localparam（当前都是 11'd25，即 50x50）。原先 11'd45 是 90x90。

  改小要注意的取舍：这个框同时就是红像素的统计窗口，框一小，参与统计的
  红像素就少、对旁边其他红色物体的抗干扰更强，测量中心也更贴合目标；
  但跟踪一旦滞后，红块更容易掉出框外，距离会显示成 "D=----CM"。
  50x50 比 40x40 的跟随框只大 5 像素余量，属于偏紧的取值。
  如果发现丢失变频繁，往回调到 60x60（half = 30）会稳一些。

  距离 = 常数 2076 / 视差（左右框中心 x 之差），再乘测距比例 cal_scale。
  视差 <2 或 >63 判为无效（挡掉 0/1 视差产生的假 2076cm 读数）。
  丢检保持 1 次更新，再丢就清 0 并把数值显示成 "D=----CM"。

  改造前的问题：屏幕上画的是固定居中框（120x90），而实际统计用的是动态框
  （90x90），两者不是一个框 —— 画面看着就是"框不动、数字乱跳"。
  本次已改成同一个框。

模式 0 的跟随框叠加
-------------------
模式 0（原始图像）上还可以叠加一个 40x40 的跟随框，对应视频里
"边缘检测 开启/关闭"那个开关：KEY3 短按开关，LED[3] 指示，跟随红色目标。
模式 7 有自己的测量框，不需要这个叠加（避免屏幕上同时出现两个不同尺寸的框）。

跟踪延迟修复（A-D-E）
---------------------
问题：目标移动时绿框明显滞后。

原因是三件事叠加，其中主因不是帧率，而是搜索窗的一个正反馈拖尾：

  [主因] 搜索窗以"上一帧中心"为中心，目标一动，红块的前沿就被窗口切掉。
  而上报的位置是包围盒中心 (minx+maxx)/2，前沿被切就等于把中心往回拽
  —— 窗口前进得比目标慢，下一帧更靠后，误差自我累积。实测框只以约
  75% 的速度跟随，越拖越远，直到红块整个跑出窗口后猛地跳一下。

  [次要] 丢锁后要冻结 3 帧才恢复（写入侧等 2 帧 + 读侧再冻 2 帧）。
  [Bug]  读写两套检测器被 "ext_l_valid || ext_r_valid" 耦合成一个开关，
         一侧锁住就把另一侧的备份检测也关掉了。

修复（A-D-E）：

  A  一阶速度预测。搜索窗中心从 prev_cx 改成 prev_cx + (prev_cx - prev2_cx)，
     即按上一帧位移外推。窗口"提前"跟着目标走，前沿不再被裁，拖尾消失。
     速度限幅 ±80 px/帧，防止一次误检把窗口甩飞。
     位置：red_target_write_track.v

  D  加快丢锁恢复。首次失配就海岸一帧（按预测位置继续上报，框不会僵住），
     同时窗口立刻开到最大 SEARCH_MAX，重新捕获从 3 帧降到 1 帧。
     读侧保持帧数 l_miss/r_miss 从 <2 改成 <1。
     位置：red_target_write_track.v + video_alg_top.v

  E  拆开左右耦合。ext_any_valid_frame 删除，改成每半屏用自己的
     ext_l_valid_frame / ext_r_valid_frame 独立门控累加与更新。
     位置：video_alg_top.v

  注意：读侧的窗口没有做预测。因为读侧 [video_alg_top.v:242] 每帧都把
  l_search_w 重置回 SEARCH_INIT_W=70（那套缩窗/扩窗逻辑因此是死代码），
  窗口恒定 ±70，比写入侧的 ±50 大，裁切偏差本来就小。如果要读侧也预测，
  是另一个小改动。

仍然存在的延迟
--------------
管线结构延迟去不掉：摄像头帧 -> DDR3 乒乓 -> LCD 读出已经是 1 帧，
检测又要等整帧结束才发布结果。

实测屏幕型号：正点原子 ALIENTEK 4.3" RGBLCD，lcd_id = 0x4342，
480x272，pclk = 12.5MHz，525x286 总计 -> 83 Hz，每帧约 12 ms。
所以屏幕这一环不是瓶颈，帧率地板比想象的低。

摄像头一侧：cam_pclk 约束写的是 25MHz（xdc 里 create_clock -period 40），
而 OV5640 的 total_h_pixel x total_v_pixel = 1800 x 1000 = 180 万 pclk/帧，
有效输出只有 240x272（6.5 万像素）——时序开销约 27 倍。
按 25MHz 算就是 72ms/帧（13.9fps），但用录像做自相关分析发现 LCD 内容在
每个手机帧（33ms）都在变、没有周期性台阶，说明实际帧率 >= 30fps，
即 cam_pclk 实际远高于 25MHz。这一项待用探头或 ILA 进一步确认。

延迟探头（怎么用板子自己量延迟）
--------------------------------
改的是 rtl/video_alg_top.v，加了一个独立的「真值检测」。

原理：
  原来的绿色框来自「写入侧跟踪器 -> meta 双口 RAM -> 读侧」这条通路，
  位置一定滞后于当前正在显示的图像。
  新加的红框是在【当前正在显示的这一帧】上现场重新检测一次红色目标算出来的
  （用的是固定的中央采集区，不受跟踪搜索窗牵连，也不经过 meta 通路）。
  所以：

      === 红框 = 目标在「现在这一帧」的真实位置 ===
      === 绿框 = 跟踪器认为的位置 ===
      === 两个框的像素距离 = 跟踪延迟的直接读数 ===

怎么用：
  1. KEY0 切到模式 0（原始图像）或模式 7（跟随测距）
  2. KEY3 短按打开探头（LED[3] 亮）
  3. 屏幕上会同时出现绿框和红框
     - 两个框重合或只差 1~3 像素 -> 跟踪基本无延迟，问题在别处
     - 红框明显领先绿框 -> 绿框的滞后量就是两者的像素距离
     - 静止时两个框是否重合？不重合说明是「系统性偏差」而不是「延迟」
       （比如 FPGA 的红色判据把皮肤也算进去了，把框心拽偏了）
  4. 快速晃动红目标，看两个框拉开多少。拉开的最大像素数 ÷ 目标每帧移动的
     像素数 ≈ 延迟帧数。

为什么不用手机录像量：
  手机只有 30fps，而 LCD 是 83Hz，33ms 的采样间隔根本分辨不出十几毫秒的
  延迟。这个探头把「时间差」直接变成「同一帧内的像素差」，不受采样率限制。

注意：红框用的是固定中央区域，如果视野里同时有两个红色物体，红框会把它们
     一起框进去（取的是并集的外接矩形）。测量时保证只有一个红目标。

时序约束补充（重要）
--------------------
加了 A-D-E 之后综合出来的网表出现 1 个保持时间(hold)违例：

  cal_scale_reg[5] -> u_lcd_rgb_top/cal_scale_sync1_reg[5]   -0.434ns

这不是功能问题，根因是既有结构：lcd_clk 由 clk_div 里的组合 mux 产生，
驱动的触发器与直接由 clk_out2 驱动的触发器之间实测有 4.5ns 的时钟插入
延迟差。工具把两者解析成同一个时钟对象，于是每个两级同步器的第一级都
过不了同频保持检查（数据路径是 0 级逻辑的裸线，绕线补不回 4.5ns）。

之前的版本 WHS 只有 +0.045ns，本来就悬在一线，改动扰动布局就翻负了。
试过 phys_opt_design + AggressiveExplore 布线，只从 -0.434 改善到 -0.323，
补不上。

最终解法：在 pin.xdc 末尾追加 6 条 set_max_delay -datapath_only 约束，
覆盖 mode / cal_scale / filter_enable / follow_enable / thr_low / thr_high
这 6 组按键参数。这些是准静态值（只在按键时变化）且都经过

按键
----
  KEY0 短按      循环 8 个模式
  KEY0 长按 1.5s 进入/退出「参数调节模式」（LED[3] 闪烁表示已进入）
  KEY3 短按      普通模式：开关模式 0 的跟随框叠加
                 调节模式：切换要调的参数（LED[1:0] 显示 0~3）
  KEY1 / KEY2    普通模式：减小/增大测距比例 cal_scale（原功能不变）
                 调节模式：减小/增大当前参数

  调节模式下的参数
    0  二值化低阈值   默认 120，范围 4 ~ 高阈值
    1  二值化高阈值   默认 255，范围 低阈值 ~ 255
    2  测距比例       默认 212，范围 8 ~ 256
    3  距离滤波开关   用 KEY1 关 / KEY2 开

  阈值每按一次变化 4。调阈值时请切到模式 1（二值化）或 2/3，
  屏幕上会实时看到效果。

已知问题 / 注意
---------------
1. bin_morph_3x3（在 red_ycbcr_morph.v 里）的行缓存写成
   `q0 <= r1`，比正规写法多打了一拍，导致三行之间横向错开一个像素，
   3x3 结构元实际是平行四边形而不是正方形。红色 mask 的形态学因此
   有约 1 像素的方向性偏差。这是改造之前就存在的，本次【没有改动】，
   因为它已经影响了红色 mask，动它会改变你已经调好的跟随/测距行为。
   新的 img_filter_pack.v 用的是对齐写法，没有复制这个偏差。

2. 综合时有一条 DRC REQP-1840 告警，指向 img_filter_pack 的行缓存
   地址由带异步复位的寄存器驱动。这是"用 x 直接索引数组"这种写法的
   固有告警，原有的 line_mem / bin_morph_3x3 也有同样问题，属于既有
   行为，不影响功能（时序已收敛，WNS=+0.994ns）。

3. 模式 7 的左右两个框是各自独立的跟随结果。如果左右目锁到了不同的
   红色物体，视差会算错、距离会跳。演示时尽量保证同一个红目标在
   左右两半都被框住。
